## Start with the problem

A case study explains why a project exists. Begin with the task or difficulty being addressed, the people who need help, and the constraints that matter. Introduce the technology after this context is clear.

For a document reader, for example, explain the need to listen to a document while moving between pages. Then describe supported files and playback controls. Readers should not need to understand the source code to understand the purpose of the application.

Separate user needs from features. Understanding a document without continuously reading a screen is a need. Pause controls, voice speed, and page selection are features that help address it.

## Explain the decisions

Describe decisions that affect how the project works. Does it process data in the browser or on a server? Does it require an account? Can users continue their work through an exported file?

A decision is easier to assess when its reasons and consequences are visible. Portable files can give users control over their work, but users also need to keep those files themselves. Explain both aspects in direct language.

### Choose relevant details

Not every code fragment belongs in a case study. Select details that explain a challenge, a decision, or a result. A long list of libraries cannot replace an explanation of how a problem was solved.

For data analysis, useful details include the data source, how the data was split, why a metric was chosen, and the limitations of the labels. Evaluation numbers need their testing context so readers do not assume that they apply everywhere.

## Show available evidence

Use genuine screenshots, working demos, or repositories that can be shared publicly. For internal projects, select documentation that does not expose personal data, account access, or operational information that has not been cleared for publication.

Do not fill a results section with estimates that look like measurements. If testing has not happened, say so. An honestly described prototype can still demonstrate the ability to design and build a solution.

### Give images context

Choose images that answer a reader's question. A home screen gives an overview; an export screenshot can explain the output. Alternative text should describe the useful information in an image rather than repeat its filename.

This portfolio stores gallery assets in each project's folder and references them in project metadata. The gallery stays hidden when no images are available. You can therefore publish a written explanation first and add visual documentation later.

## Distinguish finished work from work in progress

Project status tells visitors what they can use today. Explain what already works and what is still being developed. Finishing a documentation page does not mean the application itself is complete.

Record relevant limits as well. An application that handles one file type may not support every format. A model evaluated on one dataset may behave differently with another source.

## Review before publishing

Read the title and summary without opening the article. Together they should explain the project topic. Then check links, image dimensions, status, and consistency between the Indonesian and English versions.

Make the meaning of dates clear. A documentation date is not necessarily the date an application was built or launched. Add context when the distinction matters to the reader.

After saving changes, run the project checks and inspect the page on a narrow screen. Paragraphs that feel comfortable on desktop may be too long on a phone. Improve sentences and information order before adding decoration.

A case study does not have to be long. What matters is that readers can follow the connection between the problem, the decisions, the evidence, and the work that remains.
